# Live data is a snapshot file on R2, not an API

One Cloudflare Durable Object wakes about every 20 seconds, fetches each live feed as often as its source allows (Renfe and TRAM every time, the Metro every other time, FGC every 2 minutes; TRAM waits up to 30 minutes after it answers with no access token or refuses the one it issued, but not after no answer or an HTTP status of 500 or more), and writes one compact JSON snapshot to R2, and beside it, when they change, the operators' Alerts in a file of their own (below); viewers fetch those files through Cloudflare's CDN on a custom domain. Viewer traffic never runs our code, so cost doesn't grow with viewers and abuse can't raise the bill (their cache key ignores query strings).

## Considered Options

- **A Worker that runs on every viewer request, with an edge cache.** Rejected: every poll is billed, cache hits included, the free plan covers only about 23 viewers polling all day, and it would need rate limiting.
- **A fetcher on a home server (Umbrel) or a Hetzner machine.** Kept only as the fallback for any feed that can't be fetched within Cloudflare's limits, for example if Cloudflare's shared outgoing IPs trip FGC's quota of 5,000 requests a day per IP.

## Consequences

- The snapshot records each Network's freshness: that of the feed that covers it, which one feed can give many Networks, as Renfe's Cercanías files give Rodalies and Cercanías Madrid theirs (#248). That is what turns Trains Scheduled and raises the "live data unavailable" banner, and a feed that fails raises it for every Network it covers, though the banner names each only while its Trains are in view (ADR-0010). The map raises it too where a feed works but has had none of its Network's Trains in it for about three of its updates (five, for a Network whose feed covers others too: below) while the timetable has at least 5 of them on the map, as on 28 September 2026, when Renfe served its Cercanías feeds with a header and no Trains (#124). The snapshot still says `ok` for that feed, since the fetcher never loads the timetable, so the banner and the maintainer's checks on the snapshot no longer go by one signal alone.
- Where a feed that covers several Networks works but has none of one Network's Trains in it, the fetcher keeps that Network's last reports for two more tries, and drops them on the third. Renfe's Cercanías files drop all of Madrid's Trains now and then, with a fresh header and every other núcleo's: in 5 of 26 fetches on 4 October 2026, and 15 of 154 on the morning of 5 October, never more than two in a row. The map hears the kept reports, so for those Networks the banner for a feed with none of their Trains comes two tries later, and a Train Renfe pins to a Station stays Live through them. One placed by its GPS doesn't: the same position again counts as none (#33), so it still turns Scheduled after three missed updates. A feed that covers one Network can't drop it but by dropping all its Trains, which the map tells on its own (#124), so the fetcher keeps nothing for it. Each try that finds a Network missing, up to the one that drops its reports, goes in the fetcher's logs, which Workers Logs keeps for 7 days, to count how often (#248).
- The operators' Alerts (ADR-0012) are a second file, `alerts.json`, and not in the snapshot: they rarely change, and the page keeps every snapshot for 35 minutes. Renfe's are asked for on every run with a conditional request, which Renfe answers with 304 and no body while its file is unchanged, as it was for hours on 7 October 2026, so a file that stays the same is no failure there, though it is one for live data (#35, #49). TRAM's are asked for every 5 minutes, for each half, with the access token its adapter keeps, and never ask for one, so a refusal or a failure there never holds TRAM's live data back (#43, #51, #128). The file says when each feed was last read and how its last try went, and keeps a feed's last Alerts through tries that fail. It's written whenever a feed's Alerts change or a try at it starts or stops failing, and at least every 5 minutes, so that the time it gives each feed was last read is never more than that behind, and it's cached for a minute, as the page reads it once a minute (#339).
- It needs a domain on Cloudflare: R2's `r2.dev` URLs aren't cached and are rate-limited.
- It runs on Workers Paid ($5/month): a fetcher run measured about 12 ms of CPU, over the free plan's 10 ms. Viewer traffic never reaches a Worker, so usage stays inside the plan's included amounts.
- The Durable Object is evicted between alarms, so its throttles, tokens and each feed's last good reports live in its storage, not in memory (measured in the Cloudflare spike, see `docs/research/live-data-sources.md`).
- The fetcher runs in a Worker of its own, with no routes, rather than in the site's. A script in the site's Worker would run for every request that matches none of the site's files, and anyone can send those.
